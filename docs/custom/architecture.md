# Architecture audit

The audit covers the upstream application on `custom` at `4173074` and
the development baseline after M1 PR #1 merged at `dd36829`.

## Personalization audit

| Area | Current behavior and extension points |
| --- | --- |
| User data | [Migration 001](../../migrations/001_initial.up.sql) defines `users.avatar_url` as a string with an empty default. The [Go user model](../../internal/model/model.go), [SQLite store](../../internal/store/store.go), and [web user type](../../web/src/types.ts) carry the avatar URL, skin (`theme`), person color (`color`), and legacy `line_color`. [Migration 017](../../migrations/017_person_color_skins.up.sql) mapped legacy skins and assigned palette keys from line colors or household availability. The [YAML loader](../../internal/config/loader.go) and [exporter](../../internal/config/export.go) round-trip avatar, skin, and person color. |
| API and access | The [router](../../internal/api/router.go) exposes public user reads for the profile picker and wall display. [User handlers](../../internal/api/users.go) restrict avatar, theme, and color preference writes to the signed-in user. The avatar route accepts a nonempty URL string. The API exposes the resulting state via session and user reads, the web client caches the signed-in user in AuthContext, and the appearance controls re-render from that state. Admin People can set a URL when creating or updating a user through the general user routes. Preference handlers currently read a user and write the broader row through `UpdateUser`, so a new preference should use a targeted write to avoid overwriting other concurrent changes. |
| Image selection | [Me → Profile picture](../../web/src/pages/kid/MeSheet.tsx) previews DiceBear 9.x styles and shuffles a seed based on the user's name. [KidApp](../../web/src/pages/kid/KidApp.tsx) saves through the web API and updates auth state. [Admin People](../../web/src/components/admin/UsersTab.tsx) also generates a DiceBear URL on create and edit, so saving an edit can replace a chosen image. These URLs cause client requests to a third party and may contain the profile name. |
| Image rendering | The shared [Avatar](../../web/src/design/primitives.tsx) accepts an optional image and falls back to an initial in the user's color when the image fails. The [personal header](../../web/src/pages/kid/parts.tsx) and Me sheet supply the URL. The [profile picker](../../web/src/pages/ProfileSelection.tsx), [ambient avatar fallback](../../web/src/pages/AmbientDashboard.tsx), and People list omit it. Ambient may show a farm pet instead of an avatar. |
| Skin and background | [ThemeContext](../../web/src/ThemeContext.tsx) resolves the signed-in user's skin (Sunroom, Blocks, or Tint, with an age-based fallback) and color, and saves both through the API. [Theme CSS](../../web/src/design/themes.css) supplies scoped tokens. KidApp wraps the personal UI in `SkinScope`. Shared shells such as the picker, ambient dashboard, admin, and reports use `HouseScope`, with skin scopes available for individual cards. There is no persisted personal background setting. Farm backdrops are part of the farm scene. |

## Build and deployment audit

| Area | Findings |
| --- | --- |
| Application and storage | [Server startup](../../cmd/server/main.go) opens SQLite at `DB_PATH`, runs the embedded SQL migrations and reads optional YAML seed data for an empty database. The API handles authentication, user settings and state. React/Vite renders the UI. [Nginx](../../web/nginx.conf) serves the built frontend and proxies API, uploads and TTS. |
| Compose | [Default Compose](../../compose.yaml) has fixed container names, upstream registry tags, a config bind mount and a published web port. Renaming only the project leaves global container/image names in common. [AI development override](../../compose.dev-ai.yaml) publishes optional service ports. [API container](../../Containerfile) uses `/data/openchore.db`; the working directory matters because [the router](../../internal/api/router.go) resolves chore uploads relative to it. |
| Repository CI | [Build and Push Images](../../.github/workflows/build.yml) runs Go and Playwright checks for pushes and PRs on `main` and `release/**`. M1 adds PRs targeting `custom` to the existing test workflow. Image publishing is gated to pushes to `main` and uses upstream registry paths. The fork's ability to publish those packages has not been verified. [Publish website](../../.github/workflows/pages.yml) targets GitHub Pages on selected `main` changes and supports manual dispatch. It does not deploy the household application. No new workflow, push trigger or publishing permission is introduced in M1. |
