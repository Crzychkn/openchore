# OpenChore customization M1

M1 records the current architecture, proposes the profile image and background
designs, and establishes development and upstream integration procedures.
The audit covers `custom` at `4173074`.

## Personalization audit

| Area | Current behavior and extension points |
| --- | --- |
| User data | [Migration 001](../../migrations/001_initial.up.sql) defines `users.avatar_url` as a string with an empty default. The [Go user model](../../internal/model/model.go), [SQLite store](../../internal/store/store.go), and [web user type](../../web/src/types.ts) carry the avatar URL, skin (`theme`), person color (`color`), and legacy `line_color`. [Migration 017](../../migrations/017_person_color_skins.up.sql) mapped legacy skins and assigned palette keys from line colors or household availability. The [YAML loader](../../internal/config/loader.go) and [exporter](../../internal/config/export.go) round-trip avatar, skin, and person color. |
| API and access | The [router](../../internal/api/router.go) exposes public user reads for the profile picker and wall display. [User handlers](../../internal/api/users.go) restrict avatar, theme, and color preference writes to the signed-in user. The avatar route accepts a nonempty URL string. Admin People can set a URL when creating or updating a user through the general user routes. Preference handlers currently read a user and write the broader row through `UpdateUser`, so a new preference should use a targeted write to avoid overwriting other concurrent changes. |
| Image selection | [Me → Profile picture](../../web/src/pages/kid/MeSheet.tsx) previews DiceBear 9.x styles and shuffles a seed based on the user's name. [KidApp](../../web/src/pages/kid/KidApp.tsx) saves through the web API and updates auth state. [Admin People](../../web/src/components/admin/UsersTab.tsx) also generates a DiceBear URL on create and edit, so saving an edit can replace a chosen image. These URLs cause client requests to a third party and may contain the profile name. |
| Image rendering | The shared [Avatar](../../web/src/design/primitives.tsx) accepts an optional image and falls back to an initial in the user's color when the image fails. The [personal header](../../web/src/pages/kid/parts.tsx) and Me sheet supply the URL. The [profile picker](../../web/src/pages/ProfileSelection.tsx), [ambient avatar fallback](../../web/src/pages/AmbientDashboard.tsx), and People list omit it. Ambient may show a farm pet instead of an avatar. |
| Skin and background | [ThemeContext](../../web/src/ThemeContext.tsx) resolves the signed-in user's skin (Sunroom, Blocks, or Tint, with an age-based fallback) and color, and saves both through the API. [Theme CSS](../../web/src/design/themes.css) supplies scoped tokens. KidApp wraps the personal UI in `SkinScope`. Shared shells such as the picker, ambient dashboard, admin, and reports use `HouseScope`, with skin scopes available for individual cards. There is no persisted personal background setting. Farm backdrops are part of the farm scene. |

## Curated profile images

- Ship a small first set of original or redistribution-cleared illustrations.
  Start with animals, nature, and space, with options that read clearly at
  32 px. Review art for age suitability and light/dark contrast. Keep a
  manifest with a stable ID, localized label key, asset path, and category.
  Record the creator, source, license, and required attribution alongside the
  assets. Use optimized square WebP images with a target of 30 KiB each.
- Serve the library with the web bundle. Replace the remote preview grid
  and shuffle flow in Me with a labeled, keyboard-accessible picker that
  previews locally and has explicit Save and Use initials actions. Use
  initials for new profiles until a selection is made.
- Store a nullable catalog ID on the user and validate it against the same
  catalog on the server. Preserve `avatar_url` and the existing endpoint
  for legacy clients and imported data. Resolve a valid catalog ID first,
  then a legacy URL, then initials. An explicit Use initials action clears
  both values in one write. Treat an absent catalog ID on an older row as
  legacy behavior. Keep IDs stable across artwork revisions and define
  fallbacks for missing assets and retired entries. Round-trip the ID in
  YAML if configuration export/import is supported for the selection.
- Pass the resolved image to the personal header, Me, picker, wall fallback,
  and People list. These are household-visible images, including on public
  profile views. Keep the farm pet presentation where it already takes
  precedence. Verify keyboard selection, save and reset after sign-in and
  restart, legacy URL compatibility, and operation with the network offline
  apart from the OpenChore server.

## Per-user custom backgrounds

- Add a Background control to the personal appearance sheet. Preview the
  image with the active skin, then offer Save and Reset to skin default.
  Apply the image behind content at the personal KidApp scope only. Retain
  skin colors, focus styles, and opaque content surfaces with enough contrast
  on mobile, tablets, and in dark mode. Shared views keep their House
  styling. Switching profiles drops the previous image even if the next
  profile has no background. Missing or failed images use the skin default.
- Store a nullable, server-generated image reference per user. Return it
  through authenticated self-profile data and serve the image through an
  owner-scoped authenticated endpoint. Keep it out of public user payloads
  and the public chore-photo `/uploads/` directory. Avoid shared or
  persistent browser caching for these private images. Require a matching
  user session for upload, read, and reset, using the current self-service
  pattern.
- Accept one JPEG, PNG, or WebP per user. Initially cap input at 5 MiB and
  16 megapixels. Check file signatures and image dimensions before decoding,
  then resize to at most 1920 px on the longest edge and re-encode to strip
  metadata. Use generated filenames within a private directory under
  `/data`. Stage a new file before switching the database reference, leave
  the current image in place on failure, and remove superseded files after
  a successful switch. Handle concurrent replace/reset and clean orphaned
  files without deleting referenced files. Cover account deletion and
  include media when backing up or restoring the data volume. YAML seed
  export can omit personal media and should document that limitation.
- Use a nullable additive migration and targeted updates. Check older
  databases and defaults, invalid and oversized input, cross-user reads
  and writes, failed replacements, reset, persistence after restart, and
  contrast across the three skins. Confirm that picker, wall, admin, and
  reports remain in their existing scopes.

## Upstream synchronization

`origin` is the customization fork and `origin/custom` is the integration
branch. `upstream/main` is the source for upstream changes. Use a dedicated
development clone. From a clean checkout, add the upstream remote once
(check `git remote -v` first if it already exists), fetch both remotes, and
inspect their common history and divergence.

```bash
git remote add upstream https://github.com/liftedkilt/openchore.git
git fetch origin custom
git fetch upstream main
git merge-base origin/custom upstream/main
git log --left-right --oneline origin/custom...upstream/main
git diff --stat origin/custom...upstream/main
```

If there is no common ancestor, stop and investigate the remote and branch
history. If upstream is already an ancestor of `origin/custom`, there is
nothing to integrate. Otherwise, record the base and upstream SHAs in the
sync PR and create a fresh branch from the integration tip.

```bash
sync_branch="sync/upstream-$(git rev-parse --short upstream/main)"
git switch -c "$sync_branch" origin/custom
git merge --no-ff --no-commit upstream/main
```

Review the staged diff, especially the user model, API/auth, design tokens,
build and deployment workflows, and migration numbering. Resolve conflicts
on the sync branch and review the resulting behavior. When both branches add
the same migration version, reconcile the sequence with explicit upgrade
tests for databases that have already run either version. Use
`git merge --abort` while the merge is in progress if the integration needs
to be abandoned.

Before publishing, run `go test ./...`, run
`npm ci && npm test && npm run build` from `web/`, and run
`make test-e2e` in the disposable checkout with Chromium installed. Use
free `E2E_API_PORT` and `E2E_WEB_PORT` values (for example 18081 and 15173)
and `CI=1` so Playwright fails if it would reuse a running service. The
Playwright server deletes the checkout-local test database at startup.
Smoke-test the sync in the isolated Docker stack below, including an
upgrade from a synthetic database created on the previous custom revision.
Review failing checks and migration results before pushing and opening the PR.

```bash
git diff --cached --check
git commit -m "Merge upstream OpenChore into custom"
git push -u origin "$sync_branch"
gh pr create --base custom --head "$sync_branch" --title "Sync OpenChore upstream"
```

Recent upstream history shared with the fork stays intact through merge
commits. Integrate sync PRs with a reviewed merge that retains both parents.
If a merged sync must be reversed, use a reviewed revert PR and account for
the revert before attempting to reintroduce the same upstream commits.
Review database compatibility separately from reverting application code.
The existing image build workflow targets `main` and `release/**`, so
record test results for `custom` PRs directly unless CI coverage is added.

## Isolated Docker development

Use Docker with Compose V2 in a separate development checkout, preferably
on a development machine. The production checkout at
`/home/arthur/openchore` and its Docker project, config, credentials, images,
ports, and data belong to the live service. Use synthetic data and the
development commands below from the development checkout. The default
`compose.yaml` uses global container names and published image tags, so
changing just the project name or port would leave collisions.

```bash
mkdir -p "$HOME/src"
git clone --branch custom https://github.com/Crzychkn/openchore.git "$HOME/src/openchore-custom-dev"
cd "$HOME/src/openchore-custom-dev"
```

Save the following as `compose.m1.local.yaml` at the root of that checkout.
Use an unused project name and loopback port if starting multiple copies.

```yaml
services:
  api:
    build:
      context: .
      dockerfile: Containerfile
    working_dir: /
    environment:
      TZ: America/Los_Angeles
      CONFIG_PATH: /app/config/config.yaml
    volumes:
      - dev-data:/data
    healthcheck:
      test: ["CMD", "wget", "-q", "--spider", "http://localhost:8080/api/users"]
      interval: 5s
      timeout: 3s
      retries: 12
  web:
    build:
      context: ./web
      dockerfile: Containerfile
    ports:
      - "127.0.0.1:18080:80"
    depends_on:
      api:
        condition: service_healthy

volumes:
  dev-data:
```

Compose generates project-specific container and image names, a separate
service network, and the `openchore-custom-dev_dev-data` volume. Nginx
reaches the API as `api:8080` on that network. The API's Dockerfile stores
SQLite at `/data/openchore.db`, and the explicit working directory keeps
relative photo uploads under the same volume. AI and TTS use no credentials
in this stack. To seed a demo household, add the read-only mount
`./config/config.example.yaml:/app/config/config.yaml:ro` under the API
volumes before the first start. With an empty volume and no seed mount,
use the setup wizard to create synthetic profiles.

```bash
dev_compose() {
  docker compose --env-file /dev/null -p openchore-custom-dev -f compose.m1.local.yaml "$@"
}
dev_compose config
dev_compose up -d --build --wait
dev_compose ps
curl --fail --silent --show-error http://127.0.0.1:18080/api/users
```

Open http://127.0.0.1:18080 and verify setup or demo sign-in, profile
selection, the Today page, and appearance preferences. Restart the stack
and verify the same synthetic profiles persist.

```bash
dev_compose restart
dev_compose logs api web
dev_compose down
```

`down` retains the development volume. For a deliberately fresh database,
use `dev_compose down --volumes` only after verifying the project and volume
names and confirming that the synthetic data can be discarded.
